How Ripcord recognises and verifies a function

01
Extract the four-byte ID

Ripcord reads the implementation bytecode and records selectors that its reachable dispatcher accepts, such as 0x44c35d07.

02
Match a known signature

It hashes each signature in its local taxonomy and protocol adapters. Equal first four bytes create a candidate. No match stays unclassified.

03
Identify the guard

Calls from unrelated addresses expose recognised access-control reverts. This indicates who may call the function, not what the function does.

04
Verify the observed effect

On a fork, Ripcord executes the candidate as the controller and repeats the same working exit. Only the changed outcome confirms the restriction.

3:00–3:40 · Why the fork + differential
“The Power Map tells Ripcord that a guardian and pause route exist, but without execution their effect on a real user exit is still only a hypothesis. It would not know whether the withdrawal worked beforehand, whether the mutation was executable, or whether that exact mutation closed the exit. So Ripcord creates a real Compound position on a pinned Anvil fork and proves the withdrawal returns the asset. It restores the same state, impersonates the identified guardian only inside the fork and calls Compound’s real pause function. The same holder repeats the identical withdrawal under matched time conditions. It now reverts with Compound’s own Paused error. The fork turns a possible power into causal evidence—without touching mainnet.”
